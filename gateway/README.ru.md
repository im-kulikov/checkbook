# ИИ-шлюз Чекбука

[English version](README.md)

Необязательный помощник, который разворачивают на своём сервере. С ним приложение Чекбук может попросить модель ИИ
прочитать трудный чек. Ключа ИИ в приложении нет: оно отправляет документ шлюзу, шлюз проверяет, что запрос пришёл от
участника семьи, и только тогда вызывает поставщика ИИ ([ProxyAPI](https://proxyapi.ru), API, совместимый с OpenAI)
со своим ключом.

`server.mjs` — обычный `node:http` на Node 24 без зависимостей. Контейнер слушает только `127.0.0.1:8080`, работает
не от root, с файловой системой только для чтения и без capabilities. Перед ним ставится любой обратный прокси с HTTPS.
Состояние (кэш ключей, окна лимитов, предохранитель) живёт в памяти одного процесса, поэтому лимиты ниже точные.

Принятый риск: ключ GitHub участника семьи проходит через шлюз (по нему проверяется доступ, в журнал он не пишется).
Если ключ мог утечь — отзовите его и выпустите новый.

Файлы: `server.mjs`, `package.json`, `Dockerfile` (`node:24.22.0-alpine3.24`, закреплён по digest), `compose.yaml` (один
сервис, образ `ghcr.io/im-kulikov/checkbook-gateway:${GATEWAY_TAG}`), `.env.example`, `test/`.

## Настройка

| Переменная | Обязательна | Значение |
|---|---|---|
| `PROXYAPI_KEY` | да | ключ поставщика ИИ; только в `.env` на сервере |
| `GITHUB_REPO` | да | приватный репозиторий данных, `владелец/имя`; проходят только ключи, которые открывают именно его |
| `ALLOWED_ORIGIN` | да | адрес приложения, например `https://checkbook.example.ru`, без `/` на конце |
| `MODEL` | нет | по умолчанию `google/gemini-2.5-flash-lite` |
| `MAX_COMPLETION_TOKENS` | нет | по умолчанию `1500` |
| `PORT` | нет | по умолчанию `8080` |

Без трёх обязательных переменных шлюз не запускается и называет недостающую.

## Что делает

| Шаг | Поведение |
|---|---|
| `/healthz` | `GET` (и `HEAD`) → 200 `ok` без `Origin` и ключа (с `Access-Control-Allow-Origin: $ALLOWED_ORIGIN`, чтобы приложение показывало состояние); ProxyAPI и GitHub не вызываются, в журнал ничего не пишется. Нужен healthcheck в compose и `scripts/check-gateway.sh` |
| CORS | `OPTIONS` (отвечает сам шлюз; обратный прокси свои CORS-заголовки не добавляет) → 204 с `Access-Control-Allow-Methods: POST, OPTIONS`, `Allow-Headers: content-type, x-checkbook-key`, `Max-Age: 600`. `Origin` ≠ `ALLOWED_ORIGIN` → 403 `origin` |
| Ключ | заголовок `X-Checkbook-Key` (не `Authorization`: так проще с CORS), имя в любом регистре. Нет → 401 `no_key`; не `github_pat_…` → 401 `bad_key_format` (GitHub не спрашивается) |
| Проверка ключа | `GET https://api.github.com/repos/$GITHUB_REPO` с этим ключом: 200, `private: true`, точное имя. Иначе 401 `bad_key` / 403 `no_access` / 403 `repo_not_private`. Кэш по SHA-256 ключа: успех **2 мин** (отозванный ключ перестаёт работать не позже), отказ 1 мин; при переполнении (1000 записей) вытесняются самые старые. Лимит или сбой GitHub → 503 `github_unavailable` (не кэшируется) |
| Лимиты | **10 запросов в минуту на ключ** (скользящее окно 60 с; 11-й → 429 `rate_limited`, ProxyAPI не вызывается; запросы с плохим телом тоже считаются). **20 новых ключей в минуту** на весь шлюз (сверх → 429 `rate_limited`, GitHub не вызывается). **Предохранитель:** 5 ответов 4xx от ProxyAPI за 60 с (повторы после 429 тоже считаются) → 60 с все запросы получают 429 `ai_paused`, ProxyAPI не вызывается. Так сбойный клиент или украденный ключ не доводят общий ключ ProxyAPI до паузы на часы (20 ответов 4xx в минуту) |
| Тело | только `{"task":"extract_receipt","text"?,"image"?}`; остальные поля игнорируются. `text` ≤ 20 000 символов, `image` — `data:image/jpeg|png;base64,…`, 1 КБ ≤ размер ≤ 2 МБ после декодирования (включительно), первые байты — магия JPEG `FF D8 FF` или PNG `89 50 4E 47` → иначе 413 `too_large` / 400 `bad_json` `bad_task` `empty` `bad_text` `bad_image`. Тело больше 4 МБ пусть отсекает обратный прокси |
| ProxyAPI | `POST https://api.proxyapi.ru/v1/chat/completions`, `Authorization: Bearer $PROXYAPI_KEY`, `model=$MODEL`, `max_completion_tokens=$MAX_COMPLETION_TOKENS`, `response_format: json_object`, системная инструкция с контрактом результата (у каждого значения — цитата `ev` из документа) |
| Повторы | 429 → через 1 и 2 с (до 2 повторов, они считаются 4xx) → 429 `ai_busy`; 5xx или обрыв сети → 1 повтор → 502 `ai_unavailable`; 402 → 402 `ai_limit`; прочие 4xx не повторяются → 502 `ai_rejected`; 30 с на попытку, 55 с на всё → 504 `ai_timeout` |
| Ответ | 200 `{"result": {...}}` — JSON модели. Сверку с контрактом, цитатами `ev` и суммой из QR делает приложение |
| Журнал | одна строка на запрос в stdout: `{"keyId":"<8 hex sha256>","status":200,"ms":2140}`. Ключи, заголовки, тела и ответы ProxyAPI не пишутся никогда. Ротация: json-file, 3 × 10 МБ |

## Что делает приложение (а не шлюз)

Код клиента — `src/recognize/ai.ts`, unit-тесты с подменой `fetch`.

- Перед отправкой снимок уменьшается до ≤ 1600 px по длинной стороне, JPEG ≈ 0,8, цель < 1 МБ, EXIF удаляется. Текст
  PDF обрезается до 20 000 символов. Если всё равно больше 2 МБ — ничего не отправляется: «Файл слишком большой для ИИ».
- Не больше 10 запросов в минуту с одного устройства (скользящее окно): 11-й не отправляется, человек видит «Слишком
  много запросов к ИИ, подождите минуту» (очереди нет). Это тот же лимит, что у шлюза на ключ.
- 429 `rate_limited` и 429 `ai_paused` не повторяются (для `ai_paused` — «ИИ временно приостановлен, попробуйте через минуту»).
- 4xx от шлюза не повторяются никогда; 502/504 и обрыв сети — один повтор через 2 с.
- После 402 `ai_limit` кнопка «Уточнить с ИИ» выключена до перезапуска: владельцу учёта — «Лимит ИИ исчерпан —
  пополните баланс ProxyAPI», остальным — «Лимит ИИ исчерпан — скажите владельцу».
- Таймаут на клиенте 60 с (`AbortSignal.timeout(60_000)`); шлюз укладывается в 55 с.
- Ключ участника — только в заголовке `X-Checkbook-Key`; тело — только `{task, text?, image?}`.
- Адрес шлюза не вводится: он берётся из `import.meta.env.VITE_GATEWAY_ORIGIN` при сборке. Пустой — кнопок ИИ нет.
  Экран настроек ИИ показывает адрес и состояние (`GET /healthz`).

## Как запустить

1. Скопируйте `compose.yaml` и `.env.example` на сервер, `cp .env.example .env && chmod 600 .env`, впишите значения.
2. Запустите опубликованный образ: `GATEWAY_TAG=<sha коммита> docker compose up -d`.
3. Поставьте перед `127.0.0.1:8080` обратный прокси с HTTPS: запросы передаются как есть, CORS-заголовки не добавляются,
   тело ограничено 4 МБ, простаивающие соединения к шлюзу держатся меньше 130 с.
4. Проверьте снаружи: `ALLOWED_ORIGIN=https://checkbook.example.ru bash scripts/check-gateway.sh https://ai.example.ru`.
5. Соберите приложение с секретом репозитория `CHECKBOOK_GATEWAY_ORIGIN` = публичный адрес шлюза (без `/` на конце).

Workflow `.github/workflows/gateway.yml` гоняет тесты, публикует образ в GHCR (тег = sha коммита; пакет публичный,
секретов внутри нет) и, если в окружении `vps` есть секреты `VPS_HOST`, `VPS_PORT`, `VPS_USER`, `VPS_SSH_KEY` и
`VPS_KNOWN_HOSTS`, подключается по SSH со строгой проверкой ключа хоста и передаёт только sha коммита. Что с ним делать,
решает сервер — обычно принудительная команда в `authorized_keys`: проверяет sha, скачивает образ, перезапускает сервис
и откатывает, если `/healthz` не отвечает. Без этих секретов задача деплоя пропускается.
